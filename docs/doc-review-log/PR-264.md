## Findings

### 1. `docs/guides/` did not exist — created, deliberately small

The register, remediation and evidence features shipped with `RELEASE_NOTES.md`
recording that they exist and `README.md` listing their tables, and nothing
telling anyone how to use them. Four files now: an index, `RISK_REGISTER.md`,
`POAM.md`, `EVIDENCE.md`.

The sibling repository carries 45 guides. They are **not** copied. Most describe
screens this repository does not have, and importing them would produce
documentation for pages that do not exist — the exact failure this branch's
predecessor spent most of its time undoing. The index says so in as many words,
so the next person to look at the gap knows it was a decision rather than an
omission.

Two divergences from the sibling are called out in the guides themselves, since
both are traps for anyone porting between the repositories:

- Evidence expiry is `retention_until` here and `expires_at` there; `expires_at`
  exists in this schema but belongs to `legal_holds`.
- Evidence integrity is **SHA-384** here, per this repository's CNSA Suite 1.0
  floor, and SHA-256 in the sibling. The column is named `integrity_hash_sha256`
  in both. `EVIDENCE.md` §4 states this plainly so nobody "corrects" the column
  name or downgrades the algorithm to match it.

Verified rather than assumed: the sibling's `EVIDENCE.md` claim of SHA-256 is
**correct for that repository** — `computeFileSha256` / `createHash('sha256')`
in its `routes/evidence.js`. Only this repository uses SHA-384. Neither doc
needed fixing.

`RISK_REGISTER.md` §6 carries a **Known gap** admission rather than a silent
omission: controls, assets and objectives are read-only on the risk detail page
here, and only vendors and evidence are writable from the UI. Writing that down
was the alternative to describing a write flow this repository does not have.

### 2. `README.md`'s schema reference is accurate for this change

`evidence_control_links — Evidence-to-control linkage` still describes the table
after migration `151`; a tenant column does not change what the table is for.
Checked, unchanged, recorded here because a review that only reports problems is
not trustworthy.

The two link tables this branch's predecessor added, `risk_vendor_links` and
`risk_evidence_links`, are already listed, and `asset_control_mappings` was
corrected then from its wrong "AI-to-control mappings" gloss.

### 3. `openapi.yaml` was sixteen paths behind the API — fixed

13 → 29 paths, mirroring the sibling. Includes every reverse read
(`GET /evidence/:id/risks`, `GET /cmdb/assets/:assetId/risks`,
`GET /cmdb/risk-exposure`), the `relevance` enum, and the
`requires_poam_submission` 400 contract. The hash algorithm in the
integrity-check response description was corrected from SHA-256 to SHA-384 for
the reason in finding 1.

### 4. The IP hygiene check counted four false flags out of seven — fixed

Rule 3 tested a line against a quote character, 120-plus characters of anything,
then the same quote character — the distance from a line's first quotation mark
to any later one, not the length of a quotation. Three of this repository's
seven flags were prose in `RELEASE_NOTES.md` itself, and a fourth was a SQL seed
row holding several short quoted column values.

Delimiters are now paired in order of appearance, and an apostrophe glued to
word characters on both sides is punctuation rather than an opening delimiter.
The three genuine flags — long framework descriptions in `db/seed_hipaa_pci_gdpr.sql`,
`db/seed_iso_27001.sql` and `db/seed_soc2.sql` — still fire.

This repository runs the check only as an npm script, so nothing was failing on
it here. In the sibling it is a CI gate and the same defect was failing two jobs.
