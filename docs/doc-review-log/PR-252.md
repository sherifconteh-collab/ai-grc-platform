# Documentation review — PR #252

Performed live by a Claude Code session with direct PR/repo access (no
GitHub Action, no separate API key) — the same arrangement the PR-209 and
PR-237 logs describe.

Scope: this PR ports ControlWeaver-Pro#691 into this repo. That PR was a
follow-up to ControlWeaver-Pro#664, whose review log closed with several
items marked out of scope. This log records what the port means for *this*
repo's documentation, which has a different shape — there is no
`docs/guides/` tree here, so the doc surface is `README.md`,
`PROJECT_STATUS.md`, `RELEASE_NOTES.md` and `docs/*.md`.

## Verified already correct — no change needed

- **`RELEASE_NOTES.md` is the source of truth for version state**, and the
  four-way lock-step in `.claude/rules/releases.md` held: backend, frontend
  and electron `package.json` were all at 4.7.0 before this change and are
  all at 4.8.0 after, with both lockfiles regenerated. No drift to correct.
- **`docs/openapi.yaml`** describes the POA&M surface at the level of the
  endpoints that existed; nothing in it claimed the new routes.
- **`README.md`'s POA&M claims** are about tracking and federal reporting,
  which this PR makes *more* true rather than less. Nothing there needed
  walking back — unlike the sibling repo, this README never described a
  POA&M detail screen or an auditor review queue, so it did not have the
  "documented against the wrong artifact" problem PR-664 found there.

## The finding this port is about

Worth recording here even though the code is the fix, because it is the kind
of thing that reads as a UI gap and is not one.

The compliance gate — the rule that claiming a control is compliant requires
a written justification and produces a POA&M for an auditor — was complete
and correct in `routes/controls.js`. It was mounted on `PUT /controls/:id`.
The dashboard does not call that endpoint. It calls
`PATCH /implementations/:id/status` and `PATCH /implementations/:id/test-result`,
and neither had a single POA&M reference.

So the gate was enforced only for API clients that happened to use the other
route. From the product, a control could be marked compliant with no
justification and with nothing produced for anyone to review. The rule was
not missing, and it was not wrong; it was disconnected.

The same shape appears twice more:

- `GET /poam/framework-types` served seven framework vocabularies (FISCAM,
  ISO 27001, SOC 2, HIPAA, PCI DSS, NIST 800-53, FedRAMP) and was
  unreachable, because it was declared after `/:id` and Express bound
  `id="framework-types"`. Nothing could ever have called it, which is why
  every screen said "POA&M" regardless of the customer's framework.
- `routes/assessments/findings.js` never wrote a POA&M, leaving
  `'audit_finding'` and `'assessment'` declared in `ALLOWED_SOURCE_TYPE` and
  never written by any code path.

## A divergence the port initially got wrong

Recorded because it is the most useful thing in this log for whoever ports
between these repos next.

`routes/assessments.js` in ControlWeaver-Pro is a thin aggregator that mounts
`routes/assessments/{procedures,findings,pbc,workpapers,...}`. In this repo it
is a **3366-line monolith** with every handler inline, and the
`routes/assessments/` directory does not exist. `.claude/rules/assessment.md`
in the sibling repo describes the aggregator structure; this repo has no
equivalent rule, and the structural difference is invisible unless you look.

The first push copied `procedures.js` and `findings.js` across, which added
1137 lines of code that **nothing imports**. The auto-raise logic inside them
would never have fired — assessment results and findings would have gone on
producing no remediation, which is the exact bug this PR exists to fix, while
the diff looked like it had been fixed.

CodeQL caught it, though not for that reason: 12 high-severity
`js/missing-rate-limiting` alerts across the two files. An unmounted router has
no rate limiting because it has no anything. Chasing the alerts is what
surfaced the dead code.

Fixed by deleting the directory and wiring the auto-raise into the real inline
handlers (`POST /results`, `POST /engagements/:id/findings`).

The alerts also exposed a genuine pre-existing gap: `routes/assessments.js`
carries the whole assessment surface — procedures, results, engagements, PBC,
workpapers, findings, sign-offs — behind `authenticate` and **no rate limiting
at all**. A router-level limiter was added, the same fix already applied to
`routes/poam.js` in this branch.

## Repo-specific divergences respected during the port

These are the reasons this was not a file copy:

- **SHA-384, not SHA-256.** This repo hashes evidence with `computeFileHash`
  using SHA-384, per the CNSA Suite 1.0 floor in
  `.claude/rules/security.md`. ControlWeaver-Pro uses `computeFileSha256`.
  The ported version endpoints call this repo's function; porting the
  SHA-256 call verbatim would have quietly dropped hashing below the
  documented floor while every test still passed. The column keeps its
  legacy `integrity_hash_sha256` name in both repos — the name records the
  history, not the current algorithm, which is worth knowing before someone
  "fixes" the name.
- **`log()` / `serializeError`, not `console.error`.**
  `.claude/rules/logging.md` is explicit that this repo has no console
  bridge, so a `console.*` call goes to stdout and never reaches the
  structured stream or Sentry. All ported code uses the logger. The 12
  pre-existing `console.error` sites in `routes/evidence.js` are legacy and
  were left alone rather than swept into this diff.
- **Migration numbering.** 144–147 here, against 133/134/140/141 in the
  sibling repo. The migration headers say which upstream migration each one
  corresponds to, so the two histories can be reconciled later without
  guessing.
- This repo's own `risks.js` header comment and sidebar icons were preserved
  where the upstream files differed only cosmetically.

## Out of scope — noted, not fixed

- **`README.md` / `PROJECT_STATUS.md` feature inventories** were not
  re-verified end to end against the code in this pass. This PR's scope is
  the port; a full claim-by-claim sweep of this repo's top-level docs is its
  own piece of work, and doing it badly inside a large port is how the
  sibling repo ended up with guides describing screens that did not exist.
- **No `docs/guides/` equivalent exists here**, so the detailed user-facing
  documentation this feature now warrants — a POA&M guide, an evidence
  versioning guide, a risk register guide — has nowhere to live yet. The
  sibling repo gained `guides/RISK_REGISTER.md` in #691; this repo would
  need the directory structure first.
- **`docs/openapi.yaml` does not yet describe the new endpoints**
  (`/poam/export`, `/poam/:id/controls`, `/poam/from-risk/:riskId`,
  `/evidence/:id/versions`, `/risks/:id/poam`). Adding them is worth doing
  and is not part of this diff.
