# Releases

## Versioning

Calendar versioning: `YYYY.M.N` — four-digit year, month with no leading zero, and a same-month release counter starting at 0. Always three numeric components (never a bare `YYYY.M`), so the version stays valid SemVer — required by the Electron auto-updater (`electron/updater.js`), which compares versions via `electron-updater`/SemVer internally.

- First release in a given month → `N=0` (e.g. `2026.9.0` for the first release in September 2026).
- Another release in the same month → `N` = previous release's `N` + 1 (e.g. `2026.9.1`, `2026.9.2`, ...).
- A month with no release is simply skipped — there is no `2026.11.0` unless something actually ships that month.
- Adopted 2026-09, matching `ControlWeaver-Pro`'s same switch. Releases before the switch keep their original `X.Y.Z` semver numbers in `RELEASE_NOTES.md` history — not retroactively renumbered.

## Version sync — automated

`.github/workflows/update-docs-on-merge.yml` cuts a release on **every push to `main`** (matching `ControlWeaver-Pro`'s `release-notes.yml`): after appending the merged PR's entry to `RELEASE_NOTES.md`'s `[Unreleased]` section, that section is immediately rotated into a dated `## [YYYY.M.N] — YYYY-MM-DD` heading and `backend/package.json`, `frontend/package.json`, `electron/package.json` are all bumped to match, all in the same auto-commit (`docs: auto-update release notes and readme for PR #N [skip ci]`). A push whose `[Unreleased]` content is empty or only the placeholder blockquote (`> Changes staged but not yet released to production.`) skips the rotation and version bump — no-op, idempotent.

This means a release is cut **per merged PR**, not batched — expect a much higher release cadence than the pre-calver manual-cut history (including for routine dependabot bumps). The README version badge and "last-updated" marker are synced from the same run.

**Not automated, still manual:**
- Lockfiles (`backend/package-lock.json`, `frontend/package-lock.json`) are not regenerated by the workflow — only the `package.json` `version` field is bumped via `sed`, matching `ControlWeaver-Pro`'s own equivalent step. The lockfile's own top-level `version` field can drift from `package.json`'s (cosmetic only — `npm ci`/`npm install` don't require them to match); resync it by hand (`npm install --package-lock-only`) if it matters for a specific release.
- Git tags are never created automatically by either repo's automation — tag `vYYYY.M.N` by hand per **Tagging** below to trigger `build-release.yml`.

## RELEASE_NOTES format

Each entry has at minimum:

```
## [YYYY.M.N] — YYYY-MM-DD

### Added
### Changed
### Fixed
### Security
```

## Tagging

After merge to `main`, tag `vYYYY.M.N` to trigger `build-release.yml` which builds the Windows `.exe` installer (and `.AppImage`, `.dmg`) and publishes to GitHub Releases. The post-release smoke is `frontend/e2e/download.spec.ts`.
